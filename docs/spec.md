## 1. プロジェクトの概要

Nintendo DSの「すれ違い通信」のように、同じiPhoneアプリをインストールした人同士が近づいた際、**お気に入りの曲を自動交換**するアプリを試作する。

ユーザーはお気に入りの曲を1曲登録し、「すれ違い」をオンにしたうえで日常生活を送る。他のユーザーのiPhoneを近距離で検知でき、通信が成立した場合は、両者の曲情報を交換・保存する。次にアプリを開いた際、すれ違い履歴から新しい曲を発見できる。

**目指す体験**
1. 初回に好きな曲を1曲選ぶ。
2. 「すれ違い通信」をオンにする。
3. スマホをポケットに入れたり、別アプリを操作したりして普段どおり過ごす。
4. 同じアプリを使う人と近づいた際、可能な範囲で自動的に曲情報を交換する。
5. 後からアプリを開いて交換された曲を一覧表示する。

**PoCで明らかにしたい最重要事項：** アプリが前面にない状況、とくに画面オフのiPhone同士、または片方だけが別アプリを使用している状況で、何秒程度の接近なら、どれほどの頻度で交換に成功するのか。

### 1.1 ゴール

- iPhone実機2台で、ユーザー操作なしの相互交換を検証できる。
- 成功した交換がローカルに記録され、後から確認できる。
- 前面／他アプリ利用中／ロック画面／画面完全オフの各条件で、**発見率と交換完了率を分けて**測定できる。
- iOSの制約を踏まえて、継続開発する価値があるか判断できる。

### 1.2 今回は対象外

- Android対応、Androidとの相互通信
- 楽曲ファイルそのものの転送・再生権限の共有
- 本格的なSNS、プロフィール、フォロー、チャット
- GPSでの位置追跡やサーバーによる近隣ユーザーのマッチング
- App Store公開を必須成果物とすること
- 画面オフですべてのすれ違いを検出できるという保証

### 2.1 ユーザー画面の最小構成

**ホーム画面**
- 登録中の曲（曲名・アーティスト名）
- 「すれ違い通信」オン／オフ
- Bluetoothの許可・利用可否、現在の動作状態
- 最近交換された曲の件数

**曲登録画面**
- 初期PoCでは手入力でよい（曲名・アーティスト、任意でURL／ID）
- 後からMusicKitなどに置き換えられる構成にする

**履歴画面**
- 受け取った曲、アーティスト、交換日時
- 曲の外部リンクがあれば開ける
- 同じ相手から再受信した情報の整理
- 未確認・確認済みの区別は任意

**開発者向けデバッグ画面（PoCでは必須）**
- Bluetooth権限、Central/Peripheralの状態、スキャン・発信中か
- 発見・接続・交換・保存の件数と直近の時刻
- エラーと失敗段階
- ログのJSON/CSVエクスポート（共有シート等）
- 実験時のみ「自動交換しないで発見だけ計測」モードを持てるとよい

## 3. 技術方針（暫定、固定ではない）

| 領域 | 第一候補 | 判断・変更の余地 |
|---|---|---|
| アプリ本体 | Swift + SwiftUI | ネイティブAPIとの相性を重視。必要なら構成変更可 |
| 近距離通信 | Core Bluetooth / BLE | 代替技術が有効と実証できれば比較可 |
| 端末発信 | `CBPeripheralManager` | サービスUUIDを広告し、GATTでデータ受け渡し |
| 端末検出 | `CBCentralManager` | 指定サービスUUIDのスキャン |
| データ転送 | BLE GATT characteristic | 実装容易な最小プロトコルから開始 |
| バックグラウンド | `bluetooth-central` / `bluetooth-peripheral` | `Info.plist`で宣言。OSによる制限あり |
| 状態復元 | Core Bluetooth State Preservation & Restoration | 期待どおり再開する条件を実機確認 |
| 履歴保存 | SwiftData / SQLite / 小規模なローカルDB | 実装しやすい方法を選ぶ |
| 楽曲情報 | 初期は手入力、後にMusicKit等 | 音楽サービス認証・API制限に依存しないMVP |
| サーバー | 原則なし | 検証で必要なら追加を提案し、理由を明示 |
| iOS対応範囲 | 実験に使う実機のOSを基準に決定 | iOS 26以降のLive Activity実験は別条件で扱う |

**重要：** `MultipeerConnectivity` や `Nearby Interaction` を単に使用するだけで、iPhone同士の画面オフ自動交換が解決するとは考えない。代替採用時は「起動状態・画面オフ・操作不要・初回ペアリング不要」という条件で実機確認すること。

## 4. BLE通信の設計案

### 4.1 両端末が2つの役割を持つ

各iPhoneは同時に次の役割を担う。

- **Peripheral（発信側）**：アプリ固有のサービスUUIDを発信し、GATTサービスを公開する。
- **Central（検出側）**：同サービスUUIDを持つ端末を探して接続する。

検出した片方が接続を開始し、その1本の接続上で双方のデータをやり取りする。両方が同時に接続を開始して競合するケースは、同時接続の抑制、タイムアウト、再試行、冪等処理で扱う。

### 4.2 プロトコル案

固定の **Service UUID** と、必要な **Characteristic UUID** をアプリで定義する。以下は概念的な設計であり、実際のUUIDは実装時に生成してコードと仕様書に記録する。

| 要素 | 用途 |
|---|---|
| App Service UUID | 同じアプリを使う近隣端末の発見 |
| Read Characteristic | 相手の現在の曲ペイロードを取得 |
| Write Characteristic | 自分の曲ペイロードを相手に渡す |
| Protocol version | 将来のデータ形式変更への対応 |
| Session token | 同一接近中の重複検出抑制（永続的な個人識別子にしない） |

例：交換するデータのイメージ（**概念例。JSONを必須とはしない**）

```json
{
  "version": 1,
  "sessionToken": "temporary-random-token",
  "song": {
    "title": "Example Song",
    "artist": "Example Artist",
    "url": "https://example.com/music/123"
  }
}
```

- **音声ファイルは送らない。** 曲名・アーティスト名・曲へのリンクまたはサービスIDだけを送る。
- データは小さく保つ。文字コードや最大バイト数、MTUを超える場合の分割は実装時に決める。
- URLはHTTPS等の許可した形式に限定し、表示前にバリデーションする。
- BLE広告に曲名や個人情報を直接載せず、接続後に必要な情報を交換する。
- 「交換済み」の意味は**双方の保存成功を確認できたとき**を理想とする。初期実装でACKを省略する場合は、各端末での成功状態が食い違う可能性をログとUIに反映する。

### 4.3 交換シーケンス案

```text
iPhone A                         iPhone B
  |                                |
  | ---- BLEサービスを発信 ---->    |
  | <--- BLEサービスを発信 -----     |
  |                                |
  | -- 相手のサービスを検出         |
  | -- 接続を開始 ----------------> |
  | -- 曲Bを読み取り <------------- |
  | -- 曲Aを書き込み -------------> |
  | -- 保存確認・切断              |
  |                                |
  | 履歴に曲Bを保存                 | 履歴に曲Aを保存
  |                                |
```

接続方向が逆でも成立する設計にする。交換が途中で途切れた場合の保存・再試行・重複は明示的に扱う。

### 4.4 重複・再接続

- 同じ端末・セッションへの連続接続はクールダウン（例：10〜30分、仮値）で抑制。
- 接続が切れた場合は無制限にリトライせず、短い上限回数・バックオフを設ける。
- 同一曲が異なる相手から届いた場合は、原則として「すれ違いイベント」は別とし、履歴表示方法は後で決定できるようにする。
- 長期間の追跡につながる固定ユーザーID・固定端末IDは公開しない。
- iOSの一時的なPeripheral識別子のみで「同一人物」を長期判定できると仮定しない。必要に応じて短命のトークンとセッション内の状態を併用する。

## 5. iOSのバックグラウンド制約と実装方針

### 5.1 `Info.plist` とユーザー許可

最初の実装では、少なくとも以下を検討する。

```xml
<key>UIBackgroundModes</key>
<array>
    <string>bluetooth-central</string>
    <string>bluetooth-peripheral</string>
</array>
<key>NSBluetoothAlwaysUsageDescription</key>
<string>近くのアプリ利用者と曲を交換するためにBluetoothを利用します。</string>
```

- BLE権限は機能をオンにするタイミングで説明し、ユーザーに許可を求める。
- オフ時・権限拒否時・Bluetooth無効時の挙動を用意する。
- iOSでのバックグラウンド実行は「アプリが常に動き続ける」という意味ではない。

### 5.2 既知の制約（回避できる保証はない）

| 状態 | 仕様上の扱い |
|---|---|
| 両方がアプリ前面 | 基本的な発見・交換の検証基準 |
| 片方がアプリ前面、もう片方が画面オフ | 成立可能性はあるが、発見時間・成功率を測る |
| 両方が別アプリを使用 | 両方とも当アプリはバックグラウンド。画面点灯だけで前面相当とは扱わない |
| 片方・両方がロック画面 | OS制約下でテストする |
| 両方が画面完全オフ | **短時間ですれ違う用途には厳しい**。重要な失敗条件として測る |
| ユーザーがアプリを上スワイプ等で強制終了 | 通常のState Restorationによる再起動は期待しない |
| OSによるプロセス終了 | 保留中の適切なBLE処理とState Restorationにより復帰できる場合があるが条件付き |
| Bluetoothを設定で無効化 | 交換できない。OS状態に応じてUIを案内 |

**Apple公式仕様からの技術的注意**

1. 通常のバックグラウンドBLEスキャンは、前面時より遅くなる／頻度が制限される。複数の広告をまとめて扱う場合がある。
2. `CBPeripheralManager`でバックグラウンド広告するとローカル名は広告されず、サービスUUIDは特別な **overflow area** に移動する。このため同じアプリのiPhoneで**対象Service UUIDを指定してスキャン**する必要がある。
3. Bluetooth State Restorationは対応イベント発生時の復元支援であって、アプリを常時稼働させたり、強制終了後の動作を保証したりする機能ではない。
4. **iOS 26以降のLive Activity**があると一部のバックグラウンドBLEスキャン制限が緩和されるが、**ロック画面が完全に消灯した場合は同じ条件が続かない**。画面オフ問題の万能な解決策として採用しない。
5. 一瞬すれ違うだけでは、発見に成功しても接続・読み取り・書き込みが完了するとは限らない。**検出と交換を別指標**にする。

### 5.3 バックグラウンド状態復元

- `CBCentralManagerOptionRestoreIdentifierKey` と `CBPeripheralManagerOptionRestoreIdentifierKey` の採用を検討する。
- 復帰時にService UUID、接続済みPeripheral、再接続の状態、未完了タスクを整合させる。
- SwiftUIの起動／Sceneライフサイクルに応じ、Managerの再生成とdelegate復元を実装する。
- OSにより終了されたケースと、ユーザーが明示的に強制終了したケースを分けて実験する。
- 状態復元の成否は**実機ログ**で確認する。

### 5.4 Live Activity（比較実験）

- 優先度はP1。**先に通常のCore Bluetoothで基準値を取る。**
- 「すれ違い通信中」など正しい状態を表示し、Activityの開始／終了はユーザーの操作に整合させる。
- iOSバージョン、Dynamic Island／ロック画面の挙動、Live Activityの有無をテストログに記録する。
- Live Activityがあるだけで完全な画面オフ時の検出が高頻度になる、と仮定しない。
- この実験で明確に改善しなければ、Live Activity導入を見送ってよい。

## 6. 状態管理と保存データ

推奨する概念モデル（データベース製品や実体の型は固定しない）：

```text
MySong
- title
- artist
- urlOrServiceId?    // 任意
- updatedAt

PassbyEvent
- id                // アプリ内ローカルID
- receivedSong
- receivedAt
- exchangeStatus    // discovered / connected / received / exchanged / failed 等
- sessionToken?     // 必要な場合のみ。短期間で破棄可能
- failureReason?    // デバッグ用

BluetoothSettings
- passbyEnabled
- lastStartedAt?

DebugEvent
- timestamp
- appLifecycleState
- eventType         // scan / advertise / discovered / connect / read / write / save / error
- outcome
- details           // 個人データを最小化
```

- すれ違いモードのオン／オフは保存する。ただし**端末再起動後に自動的に完全動作することを保証しない**。
- デバッグログに曲情報や永続的な識別子を不用意に出さない。
- ログと履歴の削除手段を設ける。実験者用のログ保存期間も限定する。
- ライブラリ側の曲名／ジャケット取得にインターネットが必要な場合も、**BLE交換自体はオフラインで成立する構成**を基本とする。

## 7. 実機テスト計画（PoCの核心）

### 7.1 用意するもの

- iPhone実機 **2台以上**。Xcodeのシミュレータでは背景BLEの成立性を判定しない。
- 端末モデル、iOSバージョン、低電力モード、Bluetooth状態、アプリのビルド番号を記録。
- できれば複数のモデル・OSの組み合わせで再試験する。
- テスト時は交換する曲をAとBで別にする。

### 7.2 テストケース

| ID | iPhone A | iPhone B | 最優先の確認内容 |
|---|---|---|---|
| T-01 | アプリ前面 | アプリ前面 | BLE発見・双方向交換の基本動作 |
| T-02 | アプリ前面 | 画面オフ | 片方だけ前面の接続可能性 |
| T-03 | 画面オフ | アプリ前面 | 役割を入れ替えて再確認 |
| T-04 | 画面オフ | 別アプリを操作中 | **想定ユースケース：話しながらスマホを触っている人との交換** |
| T-05 | 別アプリを操作中 | 別アプリを操作中 | 両方バックグラウンド・画面点灯 |
| T-06 | 画面オフ | 画面オフ | 理想体験の現実的な成立率 |
| T-07 | ロック画面表示中 | 画面オフ | 完全消灯との差 |
| T-08 | 画面オフ | 画面オフ | 互いに近くで1〜5分滞在した場合 |
| T-09 | OSにより終了後の復帰 | アプリ前面 | State Restorationの成否 |
| T-10 | 明示的に強制終了 | アプリ前面 | 対応できないケースを正確に検出・記録 |
| T-11 | 同一相手と連続接近 | 任意 | 重複イベント／再接続制御 |
| T-12 | Bluetoothを無効化 | 任意 | UI状態・エラー処理 |

**接近時間の例：5秒・15秒・30秒・60秒・180秒**。最初の3条件は日常的なすれ違いを模したもの。これらはテスト条件であり、成功保証ではない。

**距離の例：1m・3m・5m**。実環境ではポケットや身体による遮蔽を含め、室内と屋外を分けて実施する。RSSIは距離の正確な測定値として扱わない。

**反復：** 条件ごとに最低10試行を推奨（初期の傾向把握用）。正式な確率推定や端末横断の一般化には追加試験が必要。

### 7.3 指標とイベントログ

- **発見率**＝検出に成功した試行数 ÷ 全試行数
- **交換完了率**＝曲データの保存が確認できた試行数 ÷ 全試行数
- **発見から交換完了までの時間**：平均・中央値・最大値・失敗ケース
- **接近開始から初回発見までの時間**
- **一方だけ交換できたケースの件数**
- **バッテリー消費の傾向**：同じ測定条件で通信オン／オフを比較（初期は定性的でもよい）
- **Live Activity有無の差**（導入した場合）

測定には、Bluetoothのコールバック・接続開始・GATT成功／失敗・ローカル保存完了のイベント時刻を使う。端末同士の時計のずれを考慮し、必要なら外部の試験ログで接近開始時刻を記録する。

### 7.4 PoCの判断基準

**技術面の最低ライン**
- T-01で、両端末で双方向に曲情報が保存できる。
- T-04〜T-06について、実測結果が再現可能な形で残る。
- 無権限・Bluetoothオフ・強制終了などで誤った「交換できた」表示をしない。

**体験の継続可否を判断する問い**
- 15秒程度の接近で、バックグラウンドの組み合わせのどれが実用的か。
- 数分の近接であれば交換が成立するか。
- 通知や画面オフ時の保証なしでも、ユーザー体験として価値があるか。
- 常時オン運用に対するバッテリーコストは許容範囲か。

最初から恣意的な成功率を「合格ライン」に設定せず、データを見て継続方針を決める。

## 8. 実装の進め方

### Phase 0：最小BLE検証

- iPhone 2台に同じサンプルアプリをインストール。
- BLEのサービス広告、スキャン、接続、read/writeを確認。
- まず前面同士で、曲の固定テキストを交換する。
- この段階ではアプリUIを最小限にし、デバッグログを優先。

**完了条件：** 2台の前面アプリ間で双方向の固定データ交換が成功する。

### Phase 1：PoCのUIと履歴

- SwiftUIなどで曲登録、通信オン／オフ、履歴、デバッグ画面を実装。
- ローカル保存、重複対策、通信エラー処理を追加。
- 実験時に手動でログを取り出せるようにする。

**完了条件：** アプリを閉じて再度開いても交換履歴が残る。

### Phase 2：バックグラウンド検証

- Core Bluetoothのバックグラウンドモードを設定。
- 必要に応じてState Restorationを追加。
- T-02〜T-12を実施し、検出率・交換完了率を記録。
- 両方がバックグラウンドの場合、成功率が低ければ現実的な制約として結果に残す。

**完了条件：** 成功・失敗の条件とボトルネックを説明できる実測レポートがある。

### Phase 3：改善案の比較（必要な場合のみ）

- Live Activityあり／なしのA/B試験。
- 発見後のGATT交換データの最適化。
- スキャン・接続のタイムアウト／リトライ調整。
- バッテリー負荷を測定。
- BLEだけでは狙った体験に届かない場合、設計変更案を提出する。

**重要：** Phase 3の改善策が成立しない場合は、無理に実装を進めず、PoCの結果をもって判断する。

## 9. 非機能要件・プライバシー

- 利用は**明示的なオプトイン**。オフにしたらBLE処理を止める。
- GPS権限・アカウント登録・電話番号・連絡先へのアクセスはMVPで不要。
- 曲情報以外のプロフィールや個人情報は交換しない。
- 個人を追跡しやすい永続的な識別子を広告しない。
- 履歴とログはユーザーが削除できる。
- Bluetoothの権限が拒否されていてもアプリ自体は起動できる。
- バッテリー消費が著しい場合は自動交換方式・利用時間帯・発信頻度などを見直す。ただしiOS側で直接制御できないパラメータを制御可能と仮定しない。
- 初期PoCは匿名・小人数の実機テストを想定。公開運用する場合は悪意あるデータ・なりすまし・スパム・DoS的な接続・プライバシーポリシー・App Store審査要件を別途検討する。

## 10. 未確定事項と変更ルール

**実装中に変更してよい事項**
- 永続化ライブラリ／データ形式／UIの構成
- 曲の入力手段（手入力、MusicKit、外部URL）
- BLEのCharacteristic構成や接続競合の解消方法
- State RestorationやLive Activityの採用タイミング
- 端末の対応OS下限、ビルド構成、ログ形式

**変更前に目的との整合性を確認すべき事項**
- BLE以外の通信手段への切り替え
- GPS／位置情報の使用
- サーバーの導入、ユーザー識別・アカウントの導入
- 手動操作を要する交換への変更
- 「すれ違い」の意味を「近くの人をサーバーで推定」に変更すること

設計変更する際は、次の4点をREADMEまたはDecision Logへ簡潔に記録する。
1. 観測された問題または根拠
2. 変更内容
3. ユーザー体験・プライバシー・バッテリーへの影響
4. 変更後の検証方法

**技術選定よりも「ユーザーが何を体験するか」と「現実にどこまで可能かを実測すること」を優先する。**

## 11. 開発成果物

PoC完了時に最低限用意するもの：

1. iPhone 2台で実行できるXcodeプロジェクト（必要な権限設定・ビルド手順付き）
2. BLEでの発見・交換が確認できる最小UI
3. 曲登録・交換履歴のローカル保存
4. 実験ログの取得・書き出し手段
5. テストケースT-01〜T-12の結果表
6. 「できたこと／できなかったこと／端末依存・OS依存／次に検証すべきこと」をまとめたREADMEまたはレポート

### 実装担当への最初の指示

> まずiPhone 2台で、前面同士のBLE GATTによる双方向交換に成功する最小構成を作ってください。SwiftUI + Core Bluetoothは第一候補ですが固定ではありません。次に片方／両方をバックグラウンドにして、特に「片方がLINEやXなどの別アプリを操作している」「両方とも画面が完全にオフ」の条件を実機で測ってください。成功率が保証できないOS挙動は必ずログを根拠として説明してください。技術選択は柔軟に変更して構いませんが、変更理由を記録してください。
